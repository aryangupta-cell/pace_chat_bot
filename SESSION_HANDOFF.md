### Key database objects discovered/used

- **`public.pace_1`** — a VIEW: `SELECT <140 cols> FROM pace_phase_1_table WHERE temp_flag_1='Include'`. This is the Looker Studio data source (confirmed by directory naming + column shapes + later confirmed via real ETL source code shared by the user directly from the production server). Grain is NOT clean 1-row-per-employee-day — it's session-level for days with both a Standard and Overtime punch (~7.5% of rows are session-level duplicates within a day).
- **`public.pace_phase_1_table`** — the real underlying TABLE (not a view) that `pace_1` filters. Populated by an external Python ETL (`pace.py`, `ps_pace.py`) running on a separate server (`aterp.xswift.biz`), NOT visible to Postgres itself (no triggers/functions in the DB). The user later pasted the FULL SOURCE of both `pace.py` and `ps_pace.py` directly into this chat (via an SSH terminal dump) — this is ground-truth for exactly how every column is computed. That dump is in the conversation history if needed again; it's very long (multiple thousand lines of SQL with extensive inline comments documenting business rules, thresholds, and historical bug fixes).
- **`public.pace_chatbot_view`** — a NEW view created during this session (the only DB write actions taken, all explicitly authorized). Built as `CREATE OR REPLACE VIEW`, iterated 3 times:
  1. First version: grain = 1 row per (employee_id, worked_day), filtered to `shift_type='Standard'` (eliminates the session-level duplication problem). Included identity, attendance flags, productivity minutes, `overall_pace_score`/`overall_std_pace_status` (originally from the OLD score columns), plus `pace_score_prev_month`/`pace_score_delta` computed via LAG() over monthly averages.
  2. Second version: swapped `overall_pace_score`/`overall_std_pace_status` source columns from the OLD legacy columns (`overall_pace_score`, `overall_std_pace_status`) to the NEWER "7:3" scoring model (`last_60_days_new_pace_score_7_3`, `new_pace_status_overall_last_60_days_7_3`) after a deep investigation (see section 3) confirmed the new columns are the better/more currently-accurate ones. Output column names kept the same (`overall_pace_score`, `overall_std_pace_status`) via aliasing so the app layer never needed to change.
  3. Third version: fixed `pace_score_prev_month`/`pace_score_delta` — they were originally built on `last_60_days_new_pace_score_7_3`, which turned out to be FROZEN per employee (zero variation across 4 months for all 353 employees), making delta always 0. Rebuilt using `new_pace_score_7_3_event_level` (the day-level, non-rolling-window score) instead — monthly average vs prior monthly average. This fixed it: 98.3% of employees (347/353) now show nonzero deltas.

**Current exact `pace_chatbot_view` definition** (as of last known state):
```sql
CREATE OR REPLACE VIEW public.pace_chatbot_view AS
WITH monthly AS (
    SELECT employee_id, date_trunc('month', worked_day)::date AS month_start,
           AVG(new_pace_score_7_3_event_level) AS avg_monthly_pace_score
    FROM public.pace_1
    WHERE shift_type = 'Standard'
    GROUP BY employee_id, date_trunc('month', worked_day)
),
monthly_with_prev AS (
    SELECT employee_id, month_start, avg_monthly_pace_score,
           LAG(avg_monthly_pace_score) OVER (PARTITION BY employee_id ORDER BY month_start) AS prev_month_avg_pace_score
    FROM monthly
)
SELECT p.employee_id, p.emp_name, p.emp_code, p.dept_id, p.dept_name,
       p.reporting_user_id, p.reporting_manager_name, p.designation, p.grade, p.doj,
       p.worked_day,
       p.lc_flag_per_day, p.el_flag_per_day, p.dh_flag_per_day,
       p.defaulter_count_per_day, p.new_pace_status_overall_last_60_days_7_3::text AS overall_std_pace_status,
       p.worked_hours, p.shift_type,
       p.productive_and_meeting_min, p.non_productive_and_whatsapp_min,
       p.whatsapp_min, p.tools_and_mails_min, p.ai_min, p.engagement_minutes,
       p.last_60_days_new_pace_score_7_3::numeric(5,2) AS overall_pace_score, p.dept_pace_score,
       p.engagement_pct, p.effectiveness_pct, p.discipline_pct, p.working_pct,
       m.prev_month_avg_pace_score::numeric AS pace_score_prev_month,
       (m.avg_monthly_pace_score - m.prev_month_avg_pace_score)::numeric AS pace_score_delta
FROM public.pace_1 p
JOIN monthly_with_prev m
    ON m.employee_id = p.employee_id AND m.month_start = date_trunc('month', p.worked_day)::date
WHERE p.shift_type = 'Standard';
```

Grain: 1 row per (employee_id, worked_day), Standard-shift only. ~26,624+ rows (grows daily, live data).

Note: `pace_chatbot_view` does NOT include `meeting_in_min`, `email_access`, or the `capped_*` columns — those live only in `pace_1`, and several query functions fall back to querying `pace_1` directly (read-only) for those, following an established pattern (`meeting_minutes_ranking()` was the first to do this).

### Column semantics learned (from the real ETL source + live data investigation)

- **Attendance**: `lc_flag_per_day`/`el_flag_per_day`/`dh_flag_per_day` = late-coming / early-leaving / deficient-hours flags, computed only on Standard-shift rows (NULL on Overtime rows). `defaulter_count_per_day` = 1 if any of LC/EL/DH fired.
- **Grain risk**: `shift_type='Standard'` is confirmed EXACTLY 1 row per (employee_id, worked_day) — zero exceptions, verified exhaustively. But it undercounts productivity minutes by ~5-30% on the ~7.3% of days that also have Overtime activity, and **completely misses 2.36% of employee-days that are Overtime-only** (no Standard row at all that day). This tradeoff was accepted knowingly.
- **Score family — TWO generations exist**:
  - OLD: `overall_pace_score`, `overall_pace_score_last_60_days`, `overall_std_pace_status`, `pace_score_overall_last_60_days_04_06_combined` (this one is dead — always 0), `pace_status_overall_last_60_days` (dead — always "No Data"). Formula: `100 - ((LC+EL flags)*100/(days*2))`, i.e., a pure attendance-based score.
  - NEW ("7:3" model): `new_pace_score_7_3_event_level` (day-level, varies daily), `overall_new_pace_score_7_3`, `last_60_days_new_pace_score_7_3` (60-worked-day rolling window, NOT calendar days), `new_pace_status_overall_last_60_days_7_3`. Formula (confirmed from real ETL source): `LEAST(100, ROUND(((avg_capped_engagement * avg_capped_effectiveness * avg_capped_working_hours * 7) + (avg_capped_discipline * 3)) * 10, 0))` — a composite of engagement, effectiveness, working-hours, and discipline, NOT just attendance.
  - Status bucket thresholds for the 7:3 status: Black <50, Red 50-64, Amber 65-79, Green 80-100.
  - `capped_engagement`, `capped_effectiveness`, `capped_discipline`, `capped_working_hours` in `pace_1` are CONFIRMED ROW-LEVEL (session-level) — an Overtime row and Standard row on the same employee-day have distinct values, not duplicated. This enabled OT-specific/WFH-specific sub-score isolation later.
- **d_score**: 84% NULL. **`ontime_completion_rate`/`responsiveness_score`/`extension_adherence_score`**: 69% NULL each (task-quality scores, only populated for a task-management-eligible employee subset).
- **`wfh_status`**: 'Work From Home' is rare — only 180 of ~30,000 rows.
- **`ps_worked_flag_day`**: binary 0/1, genuinely varies day-to-day per employee (not static), but has no prior-period baseline column, so it was implemented as a ratio (days-worked/total-days) rather than a misleading month-over-month "trend."
- **`email_access`** (in `pace_1`, sourced from `public.emp_level_email_access.email_access_1`, confirmed 0 mismatches — pure passthrough): a comma-delimited list of email addresses. The FIRST email in an employee's own list is effectively "their own manager/team-lead's shared inbox," and reverse-looking-up that email (who else's list contains it) gives "their team." **9 admin/HR emails map to ~all 590 employees** — these are treated as "universal access" and given a confirmation prompt instead of silently returning the whole company as someone's "team." Threshold: team size ≥ 90% of total active employees = universal access.
- **CRITICAL SAFETY LESSON, repeated 3 times in this session**: naive substring/ILIKE matching on names/emails is unsafe. Confirmed real collisions: `"product"` is a literal substring of `"productive"` (department "Product" false-matching inside "most productive employee"), `"atul.mangal@axestrack.com"` is a literal substring of `"pratul.mangal@axestrack.com"` (13 real employees vs. universal-access confusion). All fuzzy/substring matching in the app now requires WORD-BOUNDARY safety (via `rapidfuzz.fuzz.partial_ratio_alignment` + checking that both ends of the matched span land on real word boundaries, not mid-word) — never plain `ILIKE '%...%'` or bare `partial_ratio` scores.

## 3. INVESTIGATION PHASE SUMMARY (before any implementation)

A long series of read-only investigations preceded implementation, using background subagents extensively (large scope, kept the main conversation efficient). Key findings, in order:

1. **Broad DB inventory**: Postgres 15, 8 schemas, 542 objects. Identified `pace_1` family as the Looker source based on directory naming + column shapes.
2. **Deep dive on `pace_1`**: confirmed session-level duplication (2,003 of ~26k groups had 2-4 rows for one employee-day), confirmed `logs_on_this_day` is unreliable as a row-count validator (2.37% mismatch rate), confirmed `unique_key_4` is the true session-grain key (unique within `pace_1`, not DB-enforced).
3. **Metric grain map**: quantified exactly which columns are session-level vs. employee-day-level vs. employee-period-level within `pace_1`'s wide table (4 distinct grains mixed in one table).
4. **Standard-only hypothesis test** (exhaustive, full-dataset): confirmed `shift_type='Standard'` gives a clean 1-row-per-employee-day grain with ZERO exceptions, but productivity totals get undercounted on OT-mixed days and 2.36% of days are OT-only and get dropped entirely. This became the accepted design tradeoff for `pace_chatbot_view`.
5. **`logs_on_this_day` root cause**: traced to Control Tower department having a ~19.4% mismatch rate (vs 2.55% overall) tied to break/rotational shift patterns — confirmed via cross-referencing raw `user_shift_logs`.
6. **PACE score formula reconciliation**: tested the user-supplied Looker Studio formulas against all 9 candidate score columns; found the closest match (not exact) was Formula B over a trailing-60-day window vs `last_60_days_new_pace_score_7_3`. This was LATER SUPERSEDED by the user directly sharing the real ETL source code (`pace.py`), which gave the exact, confirmed formula (see section 2 above) — the reverse-engineering effort turned out to be very close to correct.
7. **`emp_level_email_access` investigation**: confirmed the comma-delimited email-list structure, confirmed `pace_1.email_access` is a pure passthrough (0 mismatches), confirmed the exact-match-only requirement (substring collision risk), identified the 9 universal-access admin emails.
8. **View swap + delta fix investigations**: covered in section 2 above.

At every step, the investigating agents were required to label findings FACT/INFERENCE/UNKNOWN and were explicitly forbidden from making any DB writes — confirmed via a "Database objects created/modified: NONE" footer on every report until implementation was explicitly authorized.

## 4. APPLICATION ARCHITECTURE (current state)

FastAPI Python backend + vanilla HTML/JS frontend, running locally only (no deployment). Rule-based intent matching — NO LLM involved anywhere in the query pipeline (explicit design constraint from the user, kept "free/offline").

### File structure (`app/` directory)

- **`db.py`** — `get_conn()` reads DB creds from env vars; `run_query(sql, params)` runs a SELECT, returns list of dict rows (via psycopg2 RealDictCursor).
- **`entities.py`** — all natural-language entity extraction:
  - `VIEW = "public.pace_chatbot_view"`
  - `get_dept_names()`, `get_employee_names()`, `get_manager_names()` — all `lru_cache`d, cleared via `refresh_entity_cache()`
  - `extract_department(text, fallback_text=None)` — 4-tier: (1) exact full-name match, (2) whole-phrase word-boundary match, (3) loose token-overlap match, (4) fuzzy last resort using word-boundary-safe `partial_ratio_alignment` (threshold 80, min coverage 0.7, margin 5 for tie detection). `fallback_text` retries the whole thing on raw pre-spellcheck text if the corrected text finds nothing.
  - `extract_employee(text, fallback_text=None)` — exact whole-name match, then fuzzy (no loose-token tier — this was deliberately never added, avoiding a bug class).
  - `extract_manager(text, fallback_text=None)` — exact match, then a MAJORITY-TOKEN-COVERAGE loose match (candidate needs >50% of their own name tokens present in the query, not just any single shared token — this was a bug fix, see section 5), then fuzzy.
  - `extract_month(text, default_to_current=True)` — YYYY-MM / "this month" / "last month" / month names.
  - `extract_date_range(text)` — NEWER: "yesterday" / "today" / "last week" / "this week" (ISO Monday-Sunday weeks), returns (start_date, end_date, was_mentioned).
  - `extract_limit(text)` — "top 5" / "bottom 3" parsing.
  - `split_comparison(text)` — "X vs Y" / "compare X and Y" parsing.
  - `is_self_referential(text)` — regex for "my"/"our".
  - `class Ambiguous(Exception)` — carries `.candidates` list.
- **`team.py`** — "my team" / named-person team resolution via `pace_1.email_access`. EXACT MATCH ONLY (no fuzzy — deliberate, safety-critical).
  - `resolve_employee_email(name_or_code)` → (email, emp_name, emp_code) or ambiguous-candidates tuple or not-found tuple.
  - `find_team(email)` / `resolve_team(email)` → (employee_ids, is_universal_access) via `unnest(string_to_array(email_access,','))` + exact trimmed match.
  - `resolve_named_person_team(name_or_code)` → composes the above two, used for BOTH "my team" (self) and named-manager queries ("Nikhil Kumar's team") so both paths give IDENTICAL results for the same person (this consistency was a specific bug fix — see section 5).
  - `UNIVERSAL_ACCESS_THRESHOLD = 0.9` (team size ≥ 90% of all active employees = admin).
- **`session_store.py`** — in-memory per-session-id dict: `{email, emp_name, emp_code, awaiting_identity, awaiting_admin_confirmation, pending_message, pending_message_raw}`. No persistence, no auth, resets on server restart (matches the app's "single shared access prototype" design, explicitly approved by the user).
- **`spellcheck.py`** — offline typo correction via `pyspellchecker`, run once on raw input before intent matching. Loads department names + employee names into a domain whitelist so real names/jargon are never "corrected." Handles possessive forms (`"Yadav's"`) specially — see section 5 bug #6. Explicit domain whitelist additions: `pace, whatsapp, chatgpt, dept, emp, ai, todos, todo, wfh, ot, d_score, dscore`.
- **`intents.py`** — `match_intent(text)`: ordered list of `(intent_name, [regex patterns])` tuples, checked top to bottom (specific before generic), PLUS a fuzzy fallback (`_fuzzy_match_intent`, `_CANONICAL_PHRASES` dict, `_OPPOSITE_INTENTS` safety margin so "best" and "worst" — or "improving"/"declining" — can never fuzzy-cross-match each other). ~300+ question types covered by ~80+ intent names by the end of the session. `FALLBACK_MESSAGE` shown when nothing matches.
- **`queries.py`** — all SQL query functions. Key shared infrastructure:
  - `LIMIT = 10` (default ranking size, overridable)
  - `MIN_DAYS_FOR_DELTA = 10` — minimum Standard-shift days required in BOTH current and prior month before trusting a delta (judgment call precedent, reused everywhere).
  - `CHRONIC_LATE_THRESHOLD = 3`, `NEW_JOINER_DAYS = 20`, `POTENTIAL_NEW_JOINER_DAYS = 40` — other judgment-call precedents.
  - `METRICS` dict + `metric_ranking()` — the CENTRAL generic pattern: one function drives best/worst/top-N/bottom-N for any registered metric key (pace_score, engagement, effectiveness, discipline, working_pct, late_comings, early_leavings, deficient_hours_days, defaulter_days, whatsapp_min, ai_min, tools_and_mails_min, productive_min, plus task metrics).
  - `_period_filter()` — shared SQL fragment accepting EITHER a month string OR a (start, end) date_range tuple, used by all newer category functions.
  - Category-specific functions (grown over ~4 major rounds): attendance, productivity, trend/delta (pace score, sub-scores, department, team), department aggregates/comparison, employee comparison, team summary, leave, calls, visits, WFH, tasks/todos, meetings, d_score, roster/OT, offline/device status, org info (grade/designation/tenure), score-drop/score-improvement rankings, OT-specific and WFH-specific sub-score isolation, PS-working ratio.
- **`main.py`** — `handle_message(message, session_id)` orchestrator:
  1. Resume `awaiting_identity` (identity resolution in progress)
  2. Resume `awaiting_admin_confirmation` (admin full-company confirmation in progress)
  3. Spellcheck correction (`raw_message = message` saved BEFORE correction, for fallback_text use)
  4. `intent = intents.match_intent(message)` — if None, fallback message
  5. `extract_department(message, fallback_text=raw_message)` — ambiguity check
  6. `extract_date_range()` / `extract_month()`
  7. Self-referential "my team" branch (also NOW triggers for `score_drop_ranking`/`score_improvement_alltime` intents with no department named — latest fix, see section 5 #8)
  8. Named-manager branch (uses `team.resolve_named_person_team()`, same pipeline as self-referential, with `fallback_text=raw_message` protection)
  9. Falls through to plain `answer_intent(...)`
  - `answer_intent(...)` — the central dispatcher, ~80+ intent branches, using lookup tables (`_METRIC_INTENTS`, `_EMP_FIELD_INTENTS`, `TASK_METRICS`, etc.) for generic paths. Takes a `raw_message` param, computes `fb = raw_message if raw_message != message else None` near the top, and passes `fallback_text=fb` to EVERY internal `extract_employee`/`extract_department` call (this was a full audit-and-fix pass, see section 5 #7).
- **`static/index.html`** — standalone full-page chat UI.
- **`static/dashboard.html`** — full-viewport Looker Studio iframe embed (`https://datastudio.google.com/embed/reporting/3e8589a9-dfa7-4f9b-ac5f-e1460740ea8b/page/p_8yt0aopt5d`) with a floating Intercom-style chat bubble (69×69px collapsed, 32px icon; 418×728px expanded panel, capped at 85vh/90vw so it never overflows) that reuses the SAME chat widget as the standalone page.
- **`static/chat-widget.js`** — shared chat logic (used by both index.html and dashboard.html), generates a random `session_id` per page load via `crypto.randomUUID()`, sends `{message, session_id}` to `POST /api/chat`.
- **`requirements.txt`**: `fastapi`, `uvicorn[standard]`, `psycopg2-binary`, `pydantic`, `rapidfuzz`, `pyspellchecker`.

## 5. BUGS FOUND AND FIXED (chronological, all via LIVE testing, not just code review)

1. **Sort-direction inversion**: "improving" vs "declining" query templates had `asc`/`desc` swapped — caught immediately by testing, fixed.
2. **Substring false-positive #1**: "most productive time in Accounts" incorrectly flagged department "Product" as an ambiguous match because `"product"` is a literal substring of `"productive"`. Fixed via word-boundary regex (`_contains_word`).
3. **Truncation vs. spellcheck corruption**: "bottom 2 employees of founder offi" (truncated "office") silently dropped the department filter instead of fuzzy-matching "Founders Office" or asking for clarification. Root causes: (a) the fuzzy scorer compared the WHOLE message against a single candidate (diluting the score), (b) spellcheck corrupted "offi" → "off" before fuzzy matching even ran. Fixed via `partial_ratio_alignment` (word-boundary-safe) + a `fallback_text` raw-text retry mechanism. This `fallback_text` mechanism became the template for fixing 3 more bugs later.
4. **`extract_manager` false ambiguity**: "pace score of Aryan Gupta" (not a manager) incorrectly triggered "multiple managers match" between "Fanish Kumar Gupta" and "Lokesh Gupta" purely because all three share the surname "Gupta." Fixed by requiring a STRICT MAJORITY (>50%) of a candidate's own name tokens to be present in the query, not just any single shared token.
5. **Same regression-test run found a NEW bug**: "worst attendance in Ashok Yadav's team" silently fell through to unscoped org-wide results. Root cause: spellcheck corrupted "Yadav's" → "Adam's" (the possessive-form token, apostrophe included, was never checked against the whitelist, only the bare "yadav" was). Fixed by wiring `fallback_text=raw_message` into the `extract_manager` call site in `main.py` (this specific call site had been missed when `fallback_text` was first introduced).
6. **Full audit of the `fallback_text` bug class** (explicitly requested by the user after 3 instances of the same root cause): found 13 total call sites in `main.py`, 6 of them unprotected (all inside `answer_intent` — Category A employee lookups, dept/employee comparison, admin-confirmation replay path). Fixed all 6 by threading a `raw_message` parameter through `answer_intent()`'s signature and computing `fb` once at the top; also added a parallel `pending_message_raw` session key for the admin-confirmation replay path (which previously had NO raw-text equivalent stored at all). **Also found and fixed the TRUE ROOT CAUSE at the source**: `spellcheck.py`'s possessive-form handling — `correct_typos()` now strips a trailing `'s`/`s'` BEFORE checking the whitelist/running correction, then reattaches it, so ANY whitelisted name's possessive form is protected generally, not just "Yadav." This closed the bug class rather than just patching instances.
7. **"todos" → "dodos"** (found during the 200-question expansion round): spellcheck corrupted the literal word "todos" into "dodos" since it wasn't in the domain whitelist. Fixed by adding `todos, todo, wfh, ot, d_score, dscore` to `_DOMAIN_WORDS`.
8. **Score-drop/score-improvement unscoped-by-default bug** (most recent fix): asking "biggest score drop this month" with NO department named ran unscoped across the whole company instead of defaulting to the asker's own team, unlike every other "my team"-style query. Fixed by extending the self-referential trigger condition in `handle_message` to ALSO fire when the intent is `score_drop_ranking`/`score_improvement_alltime` and no department was named — reusing the exact same identity/admin-confirmation branch as "my team."
9. **"delta" wording removed from user-facing text** (same latest round): searched all response-formatting functions in `main.py`, replaced literal "delta" in reply strings with plain English ("changed by X pts," "avg change") — kept "delta" only in internal variable/column/function names (`pace_score_delta`, `format_score_delta_rows`, etc.), per explicit instruction.
10. **"whose score dropped the most?" didn't match `score_drop_ranking`**: this and similar natural phrasings ("who dropped the most," "biggest score drop," "whose score fell the most") fell through to the fallback message. Fixed by adding ~22 trigger-phrase variants to `_SCORE_DROP_PATTERNS`/`_SCORE_IMPROVEMENT_ALLTIME_PATTERNS` in `intents.py`, plus extending `_OPPOSITE_INTENTS` and `_CANONICAL_PHRASES` so `score_drop_ranking ↔ score_improvement_alltime` now has the same fuzzy-fallback safety margin as other opposite pairs. Verified live: drop/improvement phrasings each route to the correct intent, no cross-matching.
11. **Double scope-note bug fixed** (previously listed as an open cosmetic item in section 8): root cause was `answer_intent`'s single-employee-field branch in `main.py` always appending the active team `scope_note` even when the looked-up employee IS the team owner — e.g. "PACE score for Deepak Agrawal for Deepak Agrawal's team for 2026-08: 88.0..." Fixed by suppressing the redundant team-scope portion when `team_label == f"{emp_name}'s team"`, keeping only the period note. Verified live before/after with the same repro (established team scope via "how is Deepak Agrawal's team doing," then asked "pace score of Deepak Agrawal" in the same session) — now reads "PACE score for Deepak Agrawal for 2026-08: 88.0..." Confirmed unrelated single-employee lookups are unaffected.
12. **Individual trend/lookup queries wrongly triggered team/admin-access logic**: "is [employee] improving" (or any individual-employee intent) incorrectly routed through `team.resolve_named_person_team()` — the same path used for "[name]'s team" queries — because `handle_message` in `main.py` unconditionally sent any message where `extract_manager()` matched a name through that path, for every intent. ## 7. KEY DESIGN DECISIONS / JUDGMENT CALLS (all explicitly flagged to the user, not silently made)

- `MIN_DAYS_FOR_DELTA = 10` — minimum days-of-data in both compared months before trusting any delta/trend.
- `CHRONIC_LATE_THRESHOLD = 3` late-coming days.
- `NEW_JOINER_DAYS = 20` / `POTENTIAL_NEW_JOINER_DAYS = 40` — reused directly from the real production ETL's own framing (confirmed via the pasted `pace.py` source).
- Score-family: use the NEW "7:3" columns (`last_60_days_new_pace_score_7_3` / `new_pace_status_overall_last_60_days_7_3`), not the OLD attendance-only columns — confirmed via real ETL source, not guessed.
- Grain: `shift_type='Standard'` only, accepting the tradeoff of undercounting OT-mixed days and dropping OT-only days (2.36% of employee-days).
- "My team" / named-manager team resolution: via `pace_1.email_access`'s first-listed email, reverse-looked-up, NOT via `reporting_user_id` (the latter was the ORIGINAL naive approach, later found inconsistent and replaced).
- Universal-access threshold: team size ≥ 90% of all active employees = admin, gets a confirmation prompt instead of a silent full-company answer.
- Fuzzy-match threshold: 80% similarity (`FUZZY_NAME_THRESHOLD`), minimum 70% candidate-name coverage, word-boundary-safe alignment required.
- `_OPPOSITE_INTENTS` safety margin in `intents.py` — prevents fuzzy matching from ever confusing "best"/"worst," "improving"/"declining," etc.
- Various default metrics when none is named in a query (e.g., "best department" with no metric named defaults to PACE score).
- Task-quality-score rankings exclude employees with zero scored days rather than showing pages of nulls.
- Score-drop/improvement rankings require ≥2 distinct scored days per employee.

5. Any new "my team"/named-manager feature should reuse `team.resolve_team()` / `team.resolve_named_person_team()` — do not reintroduce `reporting_user_id`-based team resolution, it was already found inconsistent and replaced once.
